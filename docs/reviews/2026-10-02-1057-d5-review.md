## 4. Product path

- **`generation_temperature` is not reachable from the admin UI.** The repo has
  two settings mechanisms: pydantic `Settings` (`config.py`, env-driven) and
  `RuntimeSettings` (`runtime.py`, DB-backed, admin-editable via
  `runtime_value("…")`). Lane A put the knob in the first. It therefore cannot
  be changed at runtime by an admin, only by an env var and a restart. See
  should-fix 1.
- `complete()` / `stream_completion()` have 14 call sites. Exactly two pass a
  temperature: `graph/review.py:166` (extraction, 0) and
  `graph/generate.py:89` (the grounded generator). The other twelve — planner,
  suggestions, chitchat, library, abstain, rewrite ×2, auto, revise_answer,
  `decisions/fallback`, `evals/judge`, `ingest/starter` — send nothing. Read
  from the call sites, not inferred from the diff.
- No test or script takes a path a user cannot: the eval harness runs the same
  graph with `source="upload"`, and the new temperature plumbing is behind the
  existing provider boundary.
- The new fixture is derived from real acceptance output but contains **no
  answers, no emails, no credentials** — only the two items' recorded
  faithfulness/verdict-relevant fields (4.8 KB). Scanned for `sk-*`,
  `Bearer …`, `password`, `api_key`, `token` and for email addresses: zero
  hits. Correctly committable.

## Should-fix

1. **`generation_temperature` is on the wrong settings mechanism.**
   `graph/generate.py:89` reads `get_settings().generation_temperature`
   (pydantic, env-only). The repo's admin-tunable path is
   `runtime_value("generation.temperature")` against `RuntimeSettings`
   (`runtime.py:114`). CLAUDE.md treats runtime settings as the way product
   knobs are adjusted, and the dispatch said "reads the runtime setting
   `generation.temperature`". As built, the knob is env-only: correct and safe
   for P2's A/B (which changes it deliberately and measurably), but it is not
   the mechanism a reviewer would expect, and the flat name
   `generation_temperature` departs from the dispatch's `generation.temperature`
   for the same reason. Not a blocker — the value is unset and the behaviour is
   identical to before — but worth aligning before the knob is actually used.
2. **The A7 counts are compared without comparing denominators.** If the fast20
   item set ever changes, `should_abstain_correct` of 7 means something
   different. `failed > 0` already refuses partial runs and `fast20_ids` pins
   the subset, so this is safe today and a hole only if the set changes
   silently. A `items`/`scored` count check on both sides of the comparison
   would close it for two lines.

## The finding that outranks both

**KI-37.** The Phase 2 runs failed the baseline's stability condition, and the
cause is a product defect rather than variance: "What does the AW-2000 package
contain?" scored 1.000 / 0.000 / 0.000 because the generator twice answered
with a list of the corpus's internal filenames. Excluding that one item the
spread is 0.0234, inside the 0.03 bar. Two runs produced a byte-identical
string, so it is reproducible and no threshold can be tuned around it.

This also **disproves the mechanism KI-32 assumed.** KI-32 attributed the
faithfulness spread to generator variance and proposed pinning extraction's
temperature. Step 2 has now run: the spread went 0.0300 → 0.0722. Pinning
extraction did not help, because the spread is not extraction variance. KI-32's
step 3 (raise `FAITHFULNESS_DROP`) is therefore the wrong lever, and is
recorded as such rather than left standing as a pending suggestion.
