**What "max rerank per attempt" is.** The KI-26 relevance gate's own number:
the maximum `rerank_score` over the post-sanitize winners (KI-70's original
note calls it "max post-sanitize rerank score"; `graph/auto.py` computes
`relevance_max = max(c.rerank_score for c in winners)`). The acceptance export
records `rerank_scores` per retrieval event with `null` where JevRerank gave
no reading, so each attempt's column is the maximum of the non-null scores
across that attempt's three query variants. One column per attempt, left to
right; a single column means the run answered on the first pass.

**What is not in these tables.** `entity_match` (KI-54) and the `sufficient`
threshold readings are **not** recoverable for these two runs: they were
recorded as `decision` events in `run_events` of the acceptance stack's own
database, `veriforge_accept_phase1b`, and that database is gone — `pg_database`
on the shared container has no `%accept%` entry and the p1b database's
`run_events` stops at 2026-10-01. `veriforge_p1b`'s decision events therefore
cover only the pre-books runs. **Entity-match values for these 57 items are
therefore assumed, not measured, in this document**; the values KI-70 quotes
for the three problem items (0.95–0.97 on `broad-alice`, 0.96–0.97 on
`broad-bovary`) are read from that entry and are not independently re-derived
here.

## 2. Why no relevance threshold moves

Confirming KI-28/KI-70's finding on this data, using the **last attempt** of
each item (the one the answer would be delivered from):

- `not_in_sources` items (should-decline, n=20 in run 1) reach relevance
  **0.71** (`outside-moby-dick`), **0.63** (`outside-holmes-boston`) and
  **0.50** (`ml-fr-outside`) — at or above the 0.60 floor.
- The `answer` items the gate loses sit at **0.35 / 0.40 / 0.43**
  (`broad-alice`, both runs), **0.57 / 0.59** (`broad-bovary`, run 1) and
  **0.39** (`amb-bovary-homais`).

The distributions overlap at every cut-off. Any threshold low enough to admit
0.35 also admits 0.39 and 0.40, and any threshold at or below 0.50 admits
three should-decline items, which would manufacture *confident wrong answers*
— strictly worse than the false abstentions it removes. `rerank_abstain` stays
at 0.60.

## 3. The rule chosen

**A question the intent classifier called `summarize` is not subject to the
relevance veto. Sufficiency and the entity check decide it alone.**

The relevance gate measures question-to-passage *lexical overlap*. "Give me
the gist of X" matches no single passage, so JevRerank scores the correct
passages low — which is why `broad-alice` sits at 0.35 while the KI-54 entity
check scores 0.97 on those same passages. For a gist question the overlap
signal is not evidence of irrelevance; it is evidence that the question is not
a lookup. So for `summarize` intent the veto is switched off and the other two
signals — which do judge whether the passages are *about* the named document —
decide alone. This is keyed on what the question **is**, not on a new number,
and it introduces no threshold to tune.

### The proof the brief asks for

Replayed on **every recorded item of both runs** (57 + 5), using each item's
last attempt, the exact decision the gate makes (`graph/auto.py:1306` and
`:1376`: answer iff `sufficient >= 0.05` **and** `relevance_ok` **and**
`entity_ok`, with the rule substituting `relevance_ok = True` when
`intent == "summarize"`):

| | items | result |
| --- | --- | --- |
| should-decline items the rule turns into an answer | **0 of 20** | the required bar |
| false abstentions the rule removes — run 1 | **2**: `broad-alice`, `broad-bovary` | both `summarize`, both `sufficient` 0.50+ |
| false abstentions the rule removes — run 2 | **1**: `broad-alice` | `summarize`, `sufficient` 0.56 |
| items whose outcome the rule changes for any other reason | **0** | |

**The entity check has to be in the replay, and it is the interesting part.**
Every recorded abstention was classified `lookup`, never `summarize`, so the
exemption never reaches one — but that alone is not the proof. Two should-decline
items clear the relevance floor outright: `outside-moby-dick` at 0.71 (held by
`sufficient` 0.04) and `outside-holmes-boston` at 0.63 (held by
`sufficient` 0.39 **and** by the KI-54 entity check — its passages were about
Sherlock Holmes, not about Mary Bostan). A replay that carried only sufficiency
and relevance would read `outside-holmes-boston` as a confident wrong answer
the run never gave. The replay therefore reads the entity check off each item's
own verdict where the other two signals leave the decision open, and the test
`test_the_entity_check_is_what_holds_the_one_abstention_that_clears_both_floors`
asserts that item by name so the column cannot quietly go missing.

**`amb-bovary-homais` is untouched, and that is correct.** It is classified
`lookup`, so the exemption does not apply and it still declines on
`sufficient` 0.13–0.16. See §4.

### What this rule does not fix, and the risk it carries

- It does not make `amb-bovary-homais` answer. That item is an evidence
  failure, not a gate one (§4).
- It does not make `broad-sherlock` or `ml-es-rocinante` answer. Those are
  KI-71's chitchat misroute, fixed structurally in phase 1c item 1.
- **The risk, stated plainly:** the exemption trusts the intent classifier on
  exactly the questions it is worst at. KI-71 is the proof that it coin-flips
  on content questions. A should-decline question phrased as a summary
  ("summarise what the sources say about Afghanistan") would be exempted from
  the relevance gate and left to `sufficient` — whose own separation margin is
  −0.06 (KI-28) — and the entity check, which is the one signal built for
  exactly this class: a passage about a different entity scores 0, and it is
  what held `outside-holmes-boston`. No such item is in the recorded set, so
  the recorded data cannot price this risk.
  `test_a_summarize_question_the_entity_check_fails_still_declines` pins the
  structure rather than a measurement, and says so in its name.

## 4. `amb-bovary-homais`: an evidence failure, and the label is wrong

`sufficient` 0.13/0.15 (run 1) and 0.14/0.16 (run 2) — stable across runs,
far under the 0.05 floor on nothing and well above it on nothing: this is the
judge saying the retrieved passages do not answer the question, twice, and the
relevance gate is beside the point.

Per the brief, `scripts/audit_labels.py` was run against the corpus, over all
**10 733** passages the test user can retrieve. It reports the item **clean**:
3 hits, no findings. That verdict is about the *query terms* (`advises`,
`advise`, `bovary`, `emma`, `eyes`) hitting passages — not about whether the
passages contain the answer. Reading the corpus directly says the item's
premise is false for **this** corpus:

| claim in `why_ambiguous` | measured over the full text of `Madame Bovary.txt` (683 723 chars) |
| --- | --- |
| "Homais, the pharmacien who recommends and supplies the drops" | `Homais` appears 168 times, `pharmacien` 120 — but **no sentence anywhere pairs the pharmacist with Emma's eyes**: `pharmacien[^.]{0,300}yeux` matches **0** times, and of the 8 speech turns in the novel that mention `yeux`, none is Homais advising her. |
| "the médecin de campagne, Rouard, whom Emma runs to when the first fails" | **`Rouard` occurs 0 times in the entire corpus**, and `médecin de la campagne` occurs 0 times. |
| "recommends and supplies the drops" for her eyes | `baume` 0, `collyre` 0, `drops` 0; all 14 occurrences of `gouttes` are rain, dew, sauce or blood. `yeux[^.]{0,300}gouttes` matches once, and it is dew falling on the writer's face. |

The eye-consultation scene is in the novel, but not in this Gutenberg
edition that the corpus was built from. `amb-bovary-homais` therefore asks a
question this corpus cannot answer, and the honest label for it is
`not_in_sources` — a corpus the run must decline on, which is the behaviour
the item was supposed to be scored against anyway.

**Relabelled `answer` → `not_in_sources`**, labels only, in
`evals/acceptance/books.json`, with the finding and the measurement recorded
in the item. No pipeline change. The class counts move with it (33/20 →
32/21 answer/abstain) and `EXPECTED_COUNTS` in `evals/acceptance_gate.py` is
updated in the same commit; PRD §5's rates are unchanged by the mix
(`math.ceil`/`//` arithmetic is over the recorded denominators).

This is a test-data fix, not a product fix: per `testing.md` and
`audit_labels.py`'s own rule, *a label that contradicts the corpus is a test
bug — fix the item, never the pipeline.* It also means KI-70's "Done when"
reduces to the two broad items answering, which is what §3's rule does.

## 5. What is still open

- KI-28's other half — a should-decline question answered — stays at 0 in both
  runs and is untouched here.
- The relevance gate still measures the wrong thing for every non-summary
  broad question. The table shows the shape: `broad-*` items at 0.35–0.43 while
  `outside-*` items reach 0.63–0.71. A signal that separated those would be
  worth having, and none of the three recorded ones does.
- Entity-match values for the books set are unrecorded (see the header). If
  the class is to be re-measured rather than replayed, the acceptance stack's
  database has to outlive the run — the same evidence loss KI-31 records for
  `our_overhead_ms`.
