# ADR-003: Latency targets per reply path, measured client-side

**Status:** Accepted, 2026-10-02.
**Full context:** PRD CH-5 and §5 (v3); TRD §7.1; reviews
`docs/reviews/2026-10-02-0400-prd-v3-review.md` (F1, F2) and `…-0420-…`.

## Context

PRD v2 set one target: Auto first token ≤ 3 s p50 / ≤ 5 s p95. It came with
the repo scaffold (2026-09-23), before Auto gained the steps that make its
answers trustworthy: query variants, the Jev rerank, sanitize, sufficiency,
conflict and the relevance gate. Measured over 132 local Auto runs
(2026-10-01/02, server-side):

| Reply path | p50 | p95 |
| --- | --- | --- |
| Single-pass answer (first token) | 7.8 s | 10.4 s |
| Decline (runs the full retry) | 12.8 s | 17.7 s |
| Held answer (TR-6, streams after review) | 23.4 s | n=1 |

The longest silent gap before the first token was 4.3 s p50 / 7.0 s p95,
because Auto doesn't publish its steps live.

One number can't describe three different paths, and hitting 3 s would
require generating before the evidence checks finish. That means answers
that are sometimes retracted, which contradicts the product's promise.

## Decision

1. Targets are **per reply path**: single-pass answers, declines, held
   answers, Fast. They're measured **client-side, from send**. Server-side
   `run_events` give the per-stage breakdown.
2. **Progress is a requirement in its own right:** no trace gap over 2 s
   before the first token or the decline.
3. Starting targets:
   - answers ≤ 5 s p50 / ≤ 8 s p95 (*provisional*)
   - declines ≤ 10 s p95 (*provisional*)
   - held answers *TBD from ≥ 10 held runs*
   - Fast ≤ 2 s p50
   - Deep complete ≤ 30 s p50
4. Provisional targets are confirmed at P3's exit. **They can be changed
   only by an owner-approved entry appended to this ADR**, never by the
   phase that has to meet them.
5. The deployed stack (P8, AWS Singapore) is authoritative; local
   measurements are indicative.

## Consequences

- P3 is "reach the targets with structural changes" (TRD §7.1), not a
  redesign. Those changes are batched embeddings, parallel searches,
  skipping variants on simple lookups, one Jev call when the sanitizer
  dropped nothing, skipping the retry when relevance is far below the
  gate, and publishing steps and sub-steps.
- No "generate while checking" path in v1.
- OKF link expansion has its own budget (≤ 500 ms p50 added), and every
  target must hold with OKF in scope.
