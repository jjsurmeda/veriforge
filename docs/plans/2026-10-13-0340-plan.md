# Plan: proven RAG, pluggable decisions, showcase — then stable, fast, UI, deploy

Owner-approved 2026-10-13. **Supersedes** `2026-10-12-0150-work-stable-fast.md`
and the unsent phase 1e brief. This plan is not amended between phases; a
change needs the owner and a dated note at the bottom.

## Product goal

- **Auto (default): adaptive + hybrid RAG**, built the way proven systems build
  it (`docs/conventions/rag-reference.md`).
- **Deep: agentic RAG** (agent loop: search → read → decide to search again or
  answer).
- **Pluggable decision models and rerankers** — Jev and others — with their
  differences shown: a comparison view and benchmark tables in the README.
- Then stable, fast, owner UI redesign, deploy. Local only until deploy.

## Rules (from what went wrong)

1. **Design first, against the reference.** Each brief starts by walking
   `rag-reference.md` for the stages it touches. No gap is found by a live run
   that reading the code would have found.
2. **Refactor without behaviour change before changing behaviour.** Never fix
   the same code twice.
3. **The bar is fixed here, once** (below). Nothing is added to a check after a
   phase starts. New findings that break no check → post-beta.
4. **Agents fix, they don't report mid-way.** Any failure of the bar: prove from
   the run's own events, fix at the root, rerun the failing ids. One report, at
   the end or at the credit/time limit.
5. **Spend only on proof.** Full check runs: at phase end, twice. While fixing:
   failing ids only. Deterministic proof (pytest, fake engines, recorded
   events) wherever it can replace a live run. Benchmarks run at phase end
   and before release, for the README — never as a lane.
6. **Done = the phase's check passes twice in a row on one commit.** A part
   that already passed twice stays closed.
7. Agents never push or merge. After review, the merge to `main` is pushed
   (CI runs; the eval-gate job spends a little credit). Push is not deploy.

## The `check-work` bar (final)

ruff, mypy --strict, pytest, vitest, OpenAPI drift, no `:free` model; eval gate
(fast20 + counterfactual) vs baseline; entity-mismatch 12/12; books acceptance:
0 confident-wrong, ≥ 90% clean declines, ≤ 5% false abstention, 0 uncited
answers, **≤ 1 content miss of 32 answerables**, smalltalk/library pass, 0
errored; **Deep set (from R2): ≥ 10 multi-hop items, ≤ 1 content miss, 0
confident-wrong, complete ≤ 30 s p50.**
**Added 2026-10-17 (owner):** held-out set: 0 confident-wrong and ≤ 5% false
abstention overall, reported per category; IsUse validation: ≤ 5% of
labelled non-answers passed as answers.

- 2026-10-17 (owner, after an outside review and the fast20 × 3 measurement):
  - **The evidence gate is redesigned, not re-tuned.** Mean-of-top-3 rubric
    grades overlap: should-decline reaches 0.56, answerables drop to 0.47
    (`docs/history/reports/2026-10-17-0140-r2a-gate-findings.md`). Proposal:
    CRAG's three-way evaluator with the reviewer as arbiter in the ambiguous
    band. It needs an ADR-006 amendment approved by the owner before code.
  - **Reviewer validation comes before that.** About 60 claims (supported,
    unsupported, contradicted) are labelled against their sources by the
    planner, and the owner spot-checks 10. Bar: the reviewer passes ≤ 5% of
    unsupported claims as supported. A reviewer that fails this cannot
    arbitrate anything.
  - **A held-out set.** About 30 new questions over documents never used in
    tuning, covering lookup, summary, compare, follow-up, missing information,
    conflict and the supported languages. They are never used to pick a
    threshold or a prompt. They are added to `check-work` (bar above).
  - **Spend control.** One OpenRouter key per dispatch, with a credit limit
    equal to the dispatch's cap. The eval gate retries a failing run up to 3×,
    so every estimate counts 3×. A dispatch runs `check-work` at most once.
  - **One-week checkpoint.** If by 2026-10-24 the books acceptance and
    held-out results haven't clearly improved, pause and revisit the scope
    before spending more.
  - **Stable phase gains** KI-76 (credits stay reserved if the process dies
    between completion and settlement) and KI-77 (CI doesn't run vitest; fixed
    now, $0).
  - **Release scorecard.** The README's quality numbers come from one
    `check-work` run on the release commit, named by its SHA. The historical
    0.976 is removed.
- 2026-10-17 (owner, later): ADR-006 accepted as a floor before generation
  plus IsUse after it, with risk-based delivery. The reviewer stays a
  faithfulness signal, so "reviewer validation" becomes **IsUse validation**:
  about 60 labelled (question, answer, sources) triples, half of them

- 2026-10-18 (owner, after the R2a-4 proof): the loop came from tuning
  thresholds on retrieval nobody had measured (ingress `lexical_weight` read
  0.00–0.04, so BM25 barely contributed). Order from here:
  1. **Retrieval first.** Label the answer chunk for each answerable item
     (books + fast20), owner spot-checks 10, measure recall@40 per config.
     Reported in R2a; a recall bar joins `check-work` from R3 (rule 3).
     **Done 2026-10-18:** 22/23 answer passages at the recorded weight (only
     nezha missed), 23/23 with an 8-row BM25 reserve (pool 48); a 0.5 weight

    gate's mean-of-3 retry runs only for correctness. Acceptance plays four

    affected ids only (≤ 10 items). R2a remainder ≈ $5 on a capped key.
  - `rag-reference.md`: a row is ✅ only with a measurement.
