## 4.1 Chat and modes: changed rows

| ID | Requirement |
| --- | --- |
| CH-2 | Auto is **single-hop**: one retrieval with several query phrasings, at most one rewrite and retry, and the trace shows each decision with its probability. Multi-hop is Deep only (CH-4). |
| CH-3 | Fast mode forces single-hop with no plan and no retry. It has **no abstention, sanitizer or ingress guardrail**, and review runs after delivery. It's an API/eval option only (CH-1), not exposed to end users. |
| CH-5 | **Progress:** after sending, the trace updates at least every 2 s until the first answer token or the decline (no silent gap over 2 s). **Single-pass answers:** first token ≤ 5 s p50 / ≤ 8 s p95 (*provisional, P3 exit*). **Declines:** decline delivered ≤ 10 s p95 (*provisional, P3 exit*). **Held answers** (TR-6: high-risk, delivered after review): delivered ≤ 25 s p95 (*provisional, P3 exit*). **Fast:** first token ≤ 2 s p50. ## 4.2 Trust: changed and new rows

| ID | Requirement |
| --- | --- |
| TR-4 | In Auto, the system retrieves once and, if the evidence is weak, rewrites and retries **once**. It abstains when **either** check fails: **sufficiency** (do the passages together answer the question?) or **answerability** (does any passage contain the answer, or, for a summary question, do the passages cover the subject?). **Until P2, answerability is the Jev relevance floor** (`rerank_abstain`). It applies only when Jev reranks; with another reranker, sufficiency alone applies. **When the generated reply itself declines, the run is recorded as an abstention and its citations are dropped (P2).** An abstention says what was found and what is missing, **carries no citations**, is written in the question's language, and offers Web or Deep. Fast mode doesn't abstain (CH-3). |
| TR-5 | When sources conflict, the answer says so and cites **the passages on each side of the conflict**; user documents outrank web by default. *(The current side assignment is a midpoint split of document ids and doesn't meet this: KI-34.)* |
| TR-8 | *(new)* When the sources support more than one answer (for example, two people who are each "the master"), the answer names each one and how it fits, instead of picking one. Prompt change, gated by the eval set, with at least 3 ambiguity items in acceptance first. |

## 4.7 OKF: Open Knowledge Format *(new)*

A bundle is a folder of markdown concept files:
- YAML frontmatter: a required `type`, plus `title`, `description`,
  `resource` and `tags`
- links between files
- v0.2 trust signals: `sources`, `generated`, `verified` (`{by, at}`),
  `status` (draft/stable/deprecated) and `stale_after`

Veriforge reads and writes the format; search stays one hybrid search.

| ID | Requirement |
| --- | --- |
| OK-0 | **Bundle handling** (the trust boundary):<ul><li>compressed ≤ 20 MB, **uncompressed ≤ 100 MB**, ≤ 2,000 concepts; archive entries with absolute paths or `..` are rejected (zip-slip)</li><li>`resource` is stored as text and **never fetched**</li><li>spec-reserved `.md` files are skipped, not rejected</li><li>re-uploading a bundle **replaces** concepts with the same bundle-relative path</li><li>links resolve by bundle-relative path, and a link to another bundle resolves only if that bundle is also in the chat's scope</li></ul> |
| OK-1 | A user uploads a bundle as chat sources, and an admin uploads one to the Shared library. Each concept becomes a source document (`format = okf`), searched in the same hybrid search as every other document. The library intent counts or groups concepts per bundle; it doesn't list every concept. |
| OK-2 | Frontmatter becomes metadata and **never enters passage text**. Server-derived attributes (`status`, `verified`, `stale`) may appear as attributes on the source wrapper the generator sees. A concept with invalid YAML or no `type` is rejected with a reason; the rest of the bundle ingests. |
| OK-3 | In Auto, passages from concepts that a retrieved concept links to directly may be added to the evidence: **one hop**, bounded by an admin limit, within the chat's scope. In Deep, the **controller's DecisionEngine `Choice` gains a `follow_link` option** (TRD §8). Linked passages pass the same sanitizer as retrieved ones. |
| OK-4 | **A link never widens access.** A link whose target is outside the chat's scope, or doesn't exist, is shown identically as "link not followed", using only the link text from the user's own source. There's no reason distinction and no target title, so the trace can't reveal whether something exists elsewhere. Covered by an ownership test. |
| OK-5 | Trust signals:<ul><li>`deprecated` concepts are excluded by a **server-side default inside scope** (admin setting, not a client filter that could widen results)</li><li>concepts past `stale_after` show a "stale" badge</li><li>an admin may enable trust ordering, which changes **ordering only**: the evidence gates always read the raw Jev score</li><li>the Sources panel and citation hover show status and who verified the concept</li></ul> |
| OK-6 | When concepts conflict, TR-5's disclosure applies, and status breaks the tie by default (via OK-2's wrapper attributes). **Depends on KI-34.** |
| OK-7 | **Export:** a reviewed answer downloads as an OKF concept.<ul><li>`sources` = its citations</li><li>`generated` = model and run</li><li>`verified` records the **actual** verdict engine (`agent/jev-…` or `agent/fallback-…`)</li><li>a human verification is an **explicit "Verify" action**, separate from thumbs-up, recorded with a stable pseudonymous id</li><li>`status`: `draft` until human-verified, then `stable`</li></ul> |
| OK-8 | Exported concepts re-import as valid OKF and keep their trust signals. |
| OK-9 | Multilingual concepts follow SR-7. |
| OK-10 | Ingestion runs **one job per bundle**: embeddings batched across concepts, one starter-question job per bundle, not per concept. |

## 5. Non-functional requirements: changed and new rows

**Acceptance corpora:**
- books (multilingual fiction)
- product manuals (AW-2000)
- an OKF bundle
- a **counterfactual corpus**: realistic documents with deliberately altered
  facts, so answers must come from the documents, not model memory

Each corpus has **≥ 30 answerable and ≥ 30 should-abstain items**, every label
proven against the corpus (a hit search for answer items, a zero-hit search
for should-abstain items). Eval corpora are never in the Shared library
(KI-24). Latency is measured locally until slice 9, then **re-measured on the
deployed stack** (P8), which is authoritative.

| Area | Target | Measured by | Status |
| --- | --- | --- | --- |
| Faithfulness | ≥ 0.90 mean per corpus | eval runner, per corpus | AW-2000 0.95–0.98; other corpora: runner support needed (P1b) |
| Minimum claim support | ≥ 0.6 on ≥ 95% of answers | eval runner summary (`min_support` field to add) | not summarised yet |
| Abstention | ≥ 90% of should-abstain items decline, per corpus | acceptance-style set, ≥ 30 items, 2 runs | books 13/14 (one mislabelled item, KI-36) |
| **Confident wrong answer** | **0**: any non-decline reply to a should-abstain item, over 3 consecutive runs | acceptance-style set | books: 0 once KI-36 is fixed |
| False abstention | ≤ 5% of answerable items, **including broad/summary questions** | acceptance-style set | 3.4–6.9% (`broad-alice`, `broad-bovary`); P2 |
| Grounding | ≥ 95% of counterfactual answers follow the document, not the real-world fact | counterfactual set with fact checks | set not built (P1b) |
| Context recall | ≥ 0.85 per corpus | eval runner (needs reference contexts) | AW-2000 0.88–0.94 |
| Progress | no trace gap > 2 s before the first token or decline | `run_events` gaps | 4.3 s p50 / 7.0 s p95; fix in P3 |
| Latency, answers | first token ≤ 5 s p50 / ≤ 8 s p95 (*provisional, P3*) | `run_events` | 7.8 / 10.4 s |
| Latency, declines | delivered ≤ 10 s p95 (*provisional, P3*) | `run_events` | 17.7 s |
| Latency, held answers | delivered ≤ 25 s p95 (*provisional, P3*) | `run_events` | 23.4 s (n=1) |
| Latency, Fast | first token ≤ 2 s p50 | `run_events`, Fast eval | not measured |
| Latency, Deep | complete ≤ 30 s p50 incl. OKF traversal, on ≥ 10 Deep items per corpus | Deep eval set (to add) | 2 runs ever |
| OKF ingestion | 500-concept bundle searchable ≤ 10 min (*provisional, OKF O2*) | ingestion timing | not built |
| OKF expansion | ≤ 500 ms p50 added to Auto, A/B with OKF in vs out of scope | timed `okf_expand` stage | not built |
| Security | ownership filter on every retrieval and every followed link; no existence oracle (OK-4) | tests (P5) | — |
| Cost | usage per answer reported, including OKF expansion and ingestion | metrics (P7) | unknown |

Decision layer, ingestion (files), availability and accessibility rows are
unchanged.

## Decisions taken in v3.1 (owner said yes where sound and achievable)

1. **Latency** as in CH-5: separate answer, decline and held-answer targets, all
   provisional until P3 measures them; progress with no gap over 2 s.
2. **Confident wrong answer** = any non-decline reply to a should-abstain item;
   0 allowed over 3 runs; ≥ 30 items per corpus.
3. **OKF ingestion** ≤ 10 min for 500 concepts, provisional until O2, with a
   bundle-level job.
4. New KIs logged: **KI-33** language detector (short French read as
   Spanish), **KI-34** TR-5 conflict sides are a midpoint split, **KI-35**
   reset email not sent, **KI-36** acceptance labels (`outside-whitman`
   mislabelled, `fact-weena` check too narrow).
